# Cookivo - wskazówki dla Claude

Komunikacja z właścicielem projektu po polsku. Komentarze w kodzie też po polsku.

## Uruchamianie

- Node 24 (`nvm use 24`), Docker Desktop. Postgres z docker-compose na porcie **5433** (5432 zajmuje lokalny Postgres 18).
- `npm run dev` - API :3000 + web :4200 (proxy `/api` → 3000). Maile w dev: Mailpit http://localhost:8025.
- Lokalny `backend/.env` ma `THROTTLE_ENABLED=false` (inaczej równoległe testy E2E trafiają w limity).

## Testy (wszystkie muszą być zielone przed uznaniem pracy za gotową)

- Backend: `npm run lint`, `npm run typecheck`, `npx vitest run`, `npm run test:e2e` (w `backend/`, baza `cookivo_test`).
- Frontend: `npx eslint src`, `npx ng test --watch=false` (w `frontend/`).
- E2E + WCAG AA: `npx playwright test --project=desktop --project=tablet --project=mobile` (w katalogu głównym).
- Po zmianach w UI: sprawdzić w przeglądarce 375 / 768 / desktop, PL i EN, jasny i ciemny motyw.

## Konwencje

- Backend zwraca **kody błędów** (`{ code: 'USERNAME_TAKEN' }`), frontend tłumaczy je kluczem `errors.<KOD>` w `frontend/public/i18n/{pl,en}.json`. Nowy kod = tłumaczenie w obu plikach (test `translations.spec.ts` pilnuje zgodności kluczy).
- Każdy endpoint domyślnie wymaga logowania; dla gości `@Public()`, uprawnienia `@Roles('ADMIN')`.
- Backend to ESM - importy względne z rozszerzeniem `.js`. Klient Prisma generowany do `backend/src/generated/prisma`.
- Frontend: standalone + signals, zoneless, Reactive Forms, Angular Material 3. Kolory tylko przez tokeny `--ck-*` ze `styles.scss`; motywy (`data-theme`: fresh / citrus / midnight / apricot / cinnamon / contrast, brak = Automatyczny wg `prefers-color-scheme` / `prefers-contrast`) to mixiny `theme-*` z tymi samymi tokenami, Material podpięty przez `mat.theme-overrides`. Nowy token = wartość w każdym mixinie `theme-*`; każda nowa para tekst/tło musi mieć kontrast AA (w `contrast` 7:1). Axe w `e2e/accessibility.spec.ts` sprawdza wszystkie motywy.
- Mobile-first: cele dotyku ≥ 44 px, właściwe `type`/`inputmode`/`autocomplete`, `env(safe-area-inset-*)`. Filtry stron przez `app-page-layout` (panel z lewej / bottom sheet).
- Hasła: polityka (12+ znaków, zxcvbn ≥ 3) jest zdublowana w `backend/src/auth/password-policy.service.ts` i `frontend/src/app/features/auth/password/password-strength.service.ts` - zmieniać razem.
- Wartości odżywcze zawsze na 100 g w standardzie etykiety UE; `null` = brak danych (nigdy nie zamieniać na 0). Reguły spójności są zdublowane w `backend/src/ingredients/nutrition.ts` i `frontend/.../ingredients/form/nutrition-validators.ts`.
- Pola liczbowe w formularzach: `type="text" inputmode="decimal"` + `parseDecimal()` (przyjmuje polski przecinek); wyświetlanie przez pipe `num` z językiem.
- Nazwy ze słowników (alergeny, kategorie, jednostki) przychodzą jako `namePl`/`nameEn` - wyświetlać pipe'em `localized`.
- Dane startowe: `npm run db:seed` (idempotentny). Katalogi składników: `backend/prisma/seed/ingredients.catalog.ts` (USDA) i `ingredients.ciqual.ts` (ANSES Ciqual 2025, Licence Ouverte 2.0 - atrybucja na karcie składnika); wartości w `ingredients.data.json` / `ciqual.data.json` z narzędzi w `prisma/seed/tools/`. Test `seed-data.spec.ts` sprawdza spójność obu źródeł razem (m.in. unikalność nazw - przed dodaniem sprawdzać istniejące pozycje po fragmentach nazw). Wyroby o zmiennym składzie (wędliny, pasztety, sosy) nie wchodzą bez weryfikacji alergenów. Plan rozbudowy: `docs/SKLADNIKI.md`. W testach e2e nie używać `TRUNCATE ... CASCADE` na `users` - wyczyści też składniki.
- Przyklejony nagłówek i dolny pasek: `scroll-padding` w `styles.scss` pilnuje, by fokus nie chował się pod nimi (WCAG 2.4.11).
- Przepisy: sumy wartości, waga i alergeny są zapisane w tabeli `recipes` i przeliczane przez `RecipeCalculatorService` (po zapisie przepisu, zmianie podprzepisu albo składnika z bazy - propagacja w górę). Czysta logika liczenia: `backend/src/recipes/recipe-math.ts`.
- Wartości przepisu: na porcję zawsze dokładne; na 100 g z opcjonalnego `cookedGrams` (waga po ugotowaniu), a bez niego z sumy surowych składników (flaga `approximate`).
- Zdjęcia: `POST /api/photos` (max 5 MB, JPG/PNG/WebP) → WebP 400/900/1600 px w `UPLOADS_DIR`, serwowane z `/api/media/`. Nieprzypięte do przepisu są sprzątane po dobie. Front zmniejsza zdjęcie przed wysyłką (`image-compress.ts`).
- Ilości w przepisach wyświetlać pipe'em `amountLabel` (polska odmiana: 1 łyżka / 2 łyżki / 5 łyżek; formy w `recipes.unitForms`).
- Testy E2E w WebKit na Windowsie (`PW_WEBKIT=1`) potrafią losowo crashować przy nawigacji ("Page crashed") - to błąd przeglądarki testowej; wiążący jest wynik CI (Linux).
- Kalkulator kcal/makro (Mifflin-St Jeor) jest zdublowany: `backend/src/profile/nutrition-calculator.ts` i `frontend/.../profile/nutrition-calculator.ts` - zmieniać razem (te same testy).
- Dane o zdrowiu (profil, alergie) wymagają zgody `HEALTH_DATA` (`403 HEALTH_CONSENT_REQUIRED`); wycofanie zgody je usuwa.
- Personalizacja list: `forMe` (domyślnie włączone dla zalogowanych, `?forMe=0` wyłącza) i sortowanie `forYou` - SQL w `backend/src/profile/personalization.ts`. Uwaga na NULL przy braku preferencji (`coalesce(..., false)`).
- Ciasteczko refresh ma ścieżkę `/api/auth` - poza nią bieżącą sesję rozpoznaje się po `sid` w access tokenie (`AuthUser.sessionId`).
- Gospodarstwa: jedno na osobę (`household_members.user_id` = PK), jeden właściciel (indeks częściowy). Przepisy `HOUSEHOLD` widzą domownicy (`householdMatesSql`, `canView(..., mates)`); przepis widoczny dla innych nie może używać prywatnych podprzepisów ani niezatwierdzonych składników. Alergie domownika tylko za jego zgodą `HOUSEHOLD_ALLERGIES` (`shareAllergies`); wycofanie zgody zdrowotnej ją wyłącza.
- Grupy znajomych (`/groups`, `backend/src/groups`): tylko dzielenie się przepisami (bez planów, zakupów, zdrowia). Widoczność `GROUPS` + `recipe_friend_groups` (autor musi być aktywnym członkiem); przepis "dla grup" widzą też domownicy autora (`canView` z `Viewer` = domownicy + aktywne grupy, SQL `sharedWithMyGroups`). Zaprasza każdy aktywny członek; zaproszony przez nie-właściciela dołącza jako `PENDING` (nie widzi przepisów, właściciel dostaje mail i akceptuje). Wyjście/usunięcie z grupy cofa udostępnienie przepisów tej osoby (`unshareRecipes`). Limity w `groups.service.ts`: 10 grup na osobę, 5 założonych, 30 osób w grupie. Podprzepis w przepisie "dla grup" musi być publiczny albo "dla grup" z gospodarstwa autora i co najmniej tymi samymi grupami (`subVisibleToAudience`).
- Import przepisu ze zdjęć (`backend/src/recipe-import`): 1-3 zdjęcia → jedno wywołanie Claude (`RecipeExtractor`, model z `RECIPE_IMPORT_MODEL`, domyślnie `claude-haiku-5-5`, structured outputs przez `zodOutputFormat`) → szkic z dopasowaniem do bazy (`isConfidentMatch`, jednostki jak `gramsFor`); nic się nie zapisuje jako przepis, formularz oznacza pozycje do sprawdzenia. Bez `ANTHROPIC_API_KEY` funkcja ukryta. Wspólna część z importem paragonów w `backend/src/ai` (`VisionService`, `AiUsageService`, `ingredient-match.ts`). Limity: `RECIPE_IMPORT_DAILY_LIMIT` / `RECEIPT_IMPORT_DAILY_LIMIT` na osobę (24 h), `RECIPE_IMPORT_MONTHLY_LIMIT` wspólny na serwis; licznik w `ai_imports` (`kind`, 90 dni, bez zdjęć). W testach zawsze podmieniać `extract` (backend) / `page.route` (Playwright) - nigdy prawdziwe API.
- Import paragonu (`backend/src/receipt-import`, front `/receipt-import?from=pantry|prices`, przycisk `ReceiptImportLink` w lodówce i cennikach): 1-4 zdjęcia → `ReceiptExtractor` (tylko żywność, ceny regularne - rabaty pomijamy) → `receipt-math.ts` (N opakowań × wielkość, grosze; towar na wagę = ułamek 1 kg / 1 l; gramatury nie zgadujemy) → szkic z dopasowaniem i propozycją cennika (nazwa sklepu, potem domyślny). Zatwierdzenie (`POST /:id/commit`) w jednej transakcji: rezerwacja importu (`committedAt`, drugie zatwierdzenie zwraca zapisany `result`), ew. nowy cennik (`PricesService.createList` - formularz `PriceListForm` tylko zapamiętuje dane), lodówka (`PantryService.addGrams` z jednostką - 2 l + 3 l = 5 l), cena (`upsertEntry`) + historia `price_observations` (usuwana z cennikiem). `scopeKey` z chwili odczytu - zmiana gospodarstwa = `409 HOUSEHOLD_CHANGED`; szkic ważny dobę. Waluta paragonu ≠ waluta cennika = ceny nie są zapisywane (front informuje). Stan importu w `ReceiptImportStore` (przeżywa wyjście z ekranu).
- Dopasowanie pozycji paragonu (`toDraft`): własne powiązanie (osoba + domownicy) → pewne domyślne → AI "SAME" (lista zatwierdzonych składników w poleceniu, `RECEIPT_CATALOG_HINTS`, serwer sprawdza nazwę) → pewna nazwa (`isConfidentMatch`); do potwierdzenia (`CONFIRM` z wybranym składnikiem, `matchSource`): niepewne domyślne → AI "SIMILAR" → nazwa z bazy na początku odczytu (`partial`). Powiązania = głosy `receipt_alias_votes` (sieć sklepu + `textKey` nazwy z paragonu, `receipt-aliases.ts`): każde zatwierdzenie pozycji (z `key`) to głos osoby; domyślne = większość, pewne od 3 głosów i 70% (`CONFIDENT_VOTES/SHARE`), bez zablokowanych kont, tylko zatwierdzone składniki. Nazwy z odczytu w `ai_imports.lines` do zatwierdzenia (czyszczone, najdłużej doba). Prośby o brakujący składnik (`backend/src/ingredient-requests`, zakładka w `/admin`, licznik spraw): pełna nazwa od użytkownika, tekst i sklep z odczytu; rozpatrzenie (wskazanie zatwierdzonego składnika) zamyka też inne otwarte prośby o ten tekst, dodaje głosy zgłaszającym i wysyła mail (`ingredientAdded` / `ingredientRequestRejected`). Formularz składnika przyjmuje `?name=`.
- Asystent (`backend/src/assistant`, front `features/assistant`: `AssistantPanel` w `app.html` - przycisk w rogu, panel z prawej / od dołu na telefonie, stan w `AssistantStore` w pamięci): zadania kończą się szkicem do zatwierdzenia przez istniejące mechanizmy. Prośba tekstowa → `AssistantAi.route` (Haiku, `ASSISTANT_ROUTE`, 30/dobę, poza tematem = odmowa bez zużycia limitu); zadania z AI (`ASSISTANT`, `ASSISTANT_DAILY_LIMIT` 5 / `ASSISTANT_MONTHLY_LIMIT` 500, osobno od importów zdjęć): plan tygodnia (kandydaci `recipes.list` `forMe` per rodzaj posiłku, kody `rN`, serwer sprawdza odpowiedź; zapis `POST /plan/apply` → `PlannerService.addMeal`, resztki = partia `toPlannerMeals`), przepisy z lodówki (braki liczy serwer), wersja przepisu (`ASSISTANT_VARIANT_MODEL` = Sonnet, `RecipeImportService.toDraft`, formularz `/recipes/new?variantOf=`, zapis z `variantOfId`). Etap 2: budżet planu (`route.budget`, koszt porcji `costPerServing` z `effectivePrices` w kontekście i w kartach), dyktowanie listy (`POST /shopping/parse`, mowa przez Web Speech API przeglądarki, `ShoppingDictation` na liście zakupów) i zamiennik „Nie mam” w trybie gotowania (`POST /substitute`, unikane alergeny tylko przy zgodzie zdrowotnej) - drobne zadania liczone jako `ASSISTANT_ROUTE`. Etap 3: plan gotowania (`/planner/prep`, `POST /assistant/prep`, 1-4 partie `PlanCook` z zakresu właściciela, Sonnet, zadanie `ASSISTANT`): model podaje tylko kolejność kroków (kody `A2`) i czasy, `prep-math.ts` naprawia kolejność w daniu, dopisuje pominięte kroki, minutnik z przepisu jest wiążący, liczy godziny (ręce robią jedno naraz, danie czeka na swój czas w tle) i okna piekarnika; widok w `prep-page` (stan w `AssistantStore.prep`, start zmienia godziny bez AI, wydruk). Szybkie akcje w panelu tylko się zaznaczają (można dopisać życzenia), wysyła „Wyślij”; panel ładowany przez `@defer (on idle)`. Uzupełnienie zakupów bez AI i bez limitu: `ShoppingService.planShortfall` (plan − lodówka − lista) + `duePurchases` z historii paragonów. Cel kcal do AI tylko przy zgodzie zdrowotnej; alergie nie idą do AI (filtr `forMe`). W testach podmieniać metody `AssistantAi` / `page.route`.
- Planer: `PlanCook` (partia: przepis ugotowany w N porcjach) + `PlanMeal` (porcje z partii zjedzone w dniu/posiłku). Dzień partii = najwcześniejszy posiłek, partia bez posiłków znika (`syncCookDate`). Plan należy do gospodarstwa albo użytkownika (CHECK `num_nonnulls`). Daty jako `@db.Date` / `YYYY-MM-DD`, na froncie bez stref (`plan-math.ts`).
- Dokładność opcjonalna: tryb prosty (porcje, równy podział na domowników i osoby bez konta) jest domyślny; tryb dokładny (`exactPortions`) dzieli posiłek wg celów kcal (`backend/src/planner/portions.ts`): cel domownika tylko za zgodą `HOUSEHOLD_TARGETS` (`shareTargets`), inaczej 2000 kcal; dzieci bez konta - wartości EFSA (`household/reference-energy.ts`). Gramy: zważony garnek > waga po ugotowaniu z przepisu > surowe składniki (szacunek).
- Lodówka i lista zakupów należą do gospodarstwa albo użytkownika (`common/owner-scope.ts`). Lista sumuje nieodhaczone pozycje tego samego składnika; z planu liczy całe partie (`PlanCook`) z zakresu dat, rozwija podprzepisy (`shopping-math.ts`) i odejmuje lodówkę (wpis bez ilości = pomiń). Ilości: sztuki (gdy składnik ma PIECE) > ml/l dla płynów > g/kg, zaokrąglone w górę. Ilość wpisana ręcznie (`amount` + `unitCode`, na liście i w lodówce także kg i l - `normalizePackageUnit`) jest pokazywana w swojej jednostce, dopóki dochodzi ilość w tej samej jednostce; ilość z planu albo w innej jednostce wraca do automatycznej (`addGrams`).
- Cenniki: ceny za opakowanie w groszach (`priceCents`) + waga opakowania w gramach (`packageGrams`, kg/l przeliczane przez `normalizePackageUnit` w `cost-math.ts` - także w lodówce i na liście zakupów; jednostki na froncie `unitOptionsWithBulk`). Koszty liczy tylko domyślny cennik właściciela (jeden na właściciela - indeks częściowy); brak cennika = `cost: null`, brakujące ceny są zawsze raportowane (`missing`), nigdy nie zgadujemy.
- Ceny ogólne (`prices/global-prices.ts` + `GlobalPricesService`): mediana cen za gram z `price_observations` źródła `RECEIPT` (ostatnie 60 dni, osobno waluta; bez zablokowanych kont - przez `ai_imports.user_id`), bez cen ponad 3× od mediany; najpierw sieć o nazwie cennika (`storeKey`), potem wszystkie. Koszty (`effectivePrices`): własny domyślny cennik, braki i brak cennika - ceny ogólne (`globalPriced`, `listName: null`, na liście `costGlobal`). W cenniku: podpowiedź `GET /api/prices/:id/global/:ingredientId` (1 kg / l / szt., "Użyj") i `stale` + `suggestedPriceCents` (własna > 90 dni, ogólna ≤ 60 dni, różnica > 10%, "Zaktualizuj"). Ręczna zmiana ceny zapisuje wpis historii `MANUAL` (nie liczy się do cen ogólnych). Nigdy nie pokazujemy, kto i kiedy kupił.
- Warianty: `variantOfId` wskazuje zawsze na pierwotny oryginał (bez łańcuchów); "Zrób własną wersję" tworzy prywatną kopię bez zdjęć. Oceny: `RecipeRating` (1-5 + komentarz, jedna na osobę, nie dla autora), średnia i liczba w `recipes.rating_avg/count` - po każdej zmianie `recomputeRatings()` (także po usunięciu konta).
- Strona przepisu przeładowuje dane po zmianie `id` (Angular używa ponownie komponentu przy przejściu przepis → przepis).
- Moderacja: zgłoszenia `Report` (RECIPE / RATING = przepis + autor opinii / USER), jedno otwarte zgłoszenie od osoby na cel (indeks częściowy). Po 3 zgłoszeniach od różnych osób treść ukrywa się sama (`hiddenReason = AUTO_REPORTS`, użytkownik: `nameHiddenAt` - nazwa pokazywana jako „Użytkownik”). Decyzja admina (`/admin`) rozstrzyga wszystkie otwarte zgłoszenia celu; autor dostaje mail, zgłaszający widzi status w ustawieniach. Ukryte opinie nie liczą się do średniej. Licznik spraw admina: `GET /api/admin/summary` (otwarte zgłoszenia liczone po celu + składniki `PENDING`) - cyfra przy nicku i w menu (`core/admin/admin-summary.service.ts`, odświeżanie przy nawigacji, powrocie do karty i co 5 min; po akcji admina `refresh(true)`).
- Blokady kont: `blockedAt` + `blockedUntil` (null = na stałe) + `blockReason`, aktywność liczy `activeBlock()` (`common/account-block.ts`). Logowanie (po poprawnym haśle) i odświeżanie zwracają `403 ACCOUNT_BLOCKED` z `until`/`reason`. `ActiveAccountGuard` sprawdza konto w bazie przy zapisach i na endpointach z `@Roles` (podmienia też `req.user.role` na bieżącą). Admina blokuje tylko SUPER_ADMIN, SUPER_ADMIN-a nikt, siebie nie (`CANNOT_MODIFY_SELF`).
- Wdrożenie (`docs/WDROZENIE.md`): hosting jchost bez SSH i bez PostgreSQL - frontend w `public_html` (Apache, `frontend/public/.htaccess`), backend przez "Setup Node.js App" (Passenger, **Node 22** - CI testuje backend na 22 i 24) pod `/api`, baza w Neon - na hostingu przez WebSocket po 443 (`DB_DRIVER=neon`, port 5432 zablokowany), lokalnie/testy/migracje przez `pg`. Backend wgrywany jako jeden plik (`npm run bundle` → `backend/deploy/`: `app.cjs` + `dist/main.mjs` + natywne `argon2`/`sharp` w `dist/node_modules`); nowy moduł natywny = dopisać do `NATIVE` w `scripts/bundle.mjs`. Zadanie `deploy` w `ci.yml` działa tylko przy `DEPLOY_ENABLED=true`.
- Dokumenty prawne: regulamin i polityka prywatności w i18n (`legal.termsDoc` / `legal.privacyDoc` - blok-tekst = akapit, blok-tablica = lista; adresy e-mail i https stają się linkami). Administrator: Patryk Ożóg (osoba prywatna), kontakt `kontakt@cookivo.pl`, konto od 16 lat. Zmiana treści = nowa data w `backend/src/legal/legal.ts` **i** `LEGAL_EFFECTIVE` we `frontend/.../legal/legal.ts` - zalogowani dostają baner z akceptacją (`GET /api/me/legal`, `POST /api/me/legal/accept`), historia zgód w ustawieniach. Opisując nowe przetwarzanie danych, uzupełnić politykę (PL i EN) i rejestr w `docs/RODO.md`. Sesje i tokeny z maili sprząta `purgeStale()` przy logowaniu (retencja z polityki).
- Fonty: Plus Jakarta Sans z `@fontsource-variable`, ikony Material Symbols Rounded okrojone do używanych (`frontend/public/fonts/`, lista `core/icons.json`) - bez zapytań do Google. Nowa ikona = `npm run icons` we `frontend/` (pobiera font na nowo); `npm run lint` i `e2e/icons.spec.ts` wyłapią brak. Tylko aktualne nazwy Material Symbols (np. `fork_spoon`, nie `restaurant_menu`).
- Strona główna: prezentacja funkcji (`features/home/feature-showcase`, dane w `showcase.data.ts`) - zakładki ARIA w grupach Podstawy / Kiedy zechcesz, bez autoplay; każdy slajd ma dostęp (Dla wszystkich / Po zalogowaniu), "Opcjonalne", gdzie to jest i "Co musisz podać". Nowa funkcja = wpis w `SLIDES` + tłumaczenia `home.showcase.slides.<key>` (karty-skróty pod hero biorą te same dane). Gość przy funkcji dla zalogowanych → `/auth/register?returnUrl=`; adres zapamiętuje `core/auth/after-signup.ts` do pierwszego logowania (link w mailu gubi query params).
